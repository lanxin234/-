# 区块链二手交易平台 —— 项目说明

## 一、选题背景

### 1.1 二手交易的信任困境

校园和社会的二手交易长期存在一个死结：

- **买家顾虑**：付了钱，卖家不发货怎么办？
- **卖家顾虑**：发了货，买家不认账怎么办？

传统解法是引入第三方平台（如闲鱼）做担保，但平台本身成为新的信任依赖点：平台可能挪用资金、可能私自修改规则、可能倒闭跑路。

### 1.2 区块链的解法

区块链提供了三个关键能力：

| 能力 | 在本项目中的作用 |
|---|---|
| **不可篡改** | 商品信息一旦上链，谁都不能偷偷改价格或描述 |
| **自动执行** | 智能合约按预设逻辑放款，不需要人工干预 |
| **去中介** | 不需要信任平台，只需要信任公开的代码 |

于是我们把「担保」这个职责从平台手里，交给了智能合约。

### 各层职责

**前端层**：纯 HTML/CSS/JS 单文件，负责展示和交互。不直接接触区块链，通过后端 API 与链通信。图表用 Chart.js（本地文件，不依赖外网）。登录令牌保存在 `localStorage`，`api()` 封装统一附加 `Authorization` 头并处理续期/过期。

**后端层**：Flask 提供 REST 接口。核心职责：
- **认证鉴权**——校验密码（scrypt）、签发/校验令牌、拦截越权请求（`auth.py`）
- **账户映射**——把已验证的用户名映射到链上地址（网页用户不可能手输 42 位十六进制地址）
- **图片存储**——按内容哈希命名保存到 `uploads/`
- **事件解析**——从链上日志重建交易时间线
- **实时统计**——遍历链上数据聚合出看板指标

**合约层**：项目的核心。所有业务规则写在这里，包括权限校验、资金托管、状态流转。同时通过 `emit` 事件为上层提供可追溯的数据源。

**链层**：eth-tester 提供的内存以太坊，完全兼容 EVM。重启即重置，适合反复演示。

## 三、智能合约设计

### 3.1 数据结构

```solidity
// 商品：从在售到售出的完整生命周期
struct Item {
    uint256 id;             // 商品编号
    string  name;           // 名称
    string  description;    // 描述
    uint256 price;          // 价格（wei）
    address payable seller; // 卖家地址
    address buyer;          // 买家地址
    ItemStatus status;      // 状态
    uint256 createdAt;      // 上架时间
}

// 用户：信誉系统的载体
struct User {
    string  nickname;
    uint256 soldCount;      // 卖出数
    uint256 boughtCount;    // 买入数
    uint256 ratingSum;      // 评分总和
    uint256 ratingCount;    // 评价次数
    bool    registered;
}
```

### 3.2 商品状态机

商品在生命周期中只有四种状态，且流转方向受到严格控制：

```
        listItem()
            ↓
      ┌──────────┐
      │  OnSale  │──removeItem()──→ ┌──────────┐
      │  在售    │                   │ Removed  │
      └────┬─────┘                   │  已下架  │
           │ buyItem()               └──────────┘
           ↓
      ┌──────────┐
      │ InEscrow │  ← 钱在合约里，卖家拿不到
      │ 交易中   │
      └────┬─────┘
           │ confirmReceived()
           ↓
      ┌──────────┐
      │   Sold   │  ← 货款已放给卖家
      │  已售出  │
      └──────────┘
```

**为什么状态机很重要**：`buyItem()` 里有 `require(item.status == ItemStatus.OnSale)`，意味着**同一件商品不可能被卖两次**。这就是区块链防重复交易的方式——靠状态检查，而不是靠数据库锁。

### 3.3 核心函数剖析

#### buyItem() —— 托管的关键

```solidity
function buyItem(uint256 _itemId) public payable onlyRegistered itemExists(_itemId) {
    Item storage item = items[_itemId];

    require(item.status == ItemStatus.OnSale, "Item is not on sale");
    require(item.seller != msg.sender, "Cannot buy your own item");
    require(msg.value == item.price, "Payment amount does not match price");

    item.buyer = msg.sender;
    item.status = ItemStatus.InEscrow;
    // 注意：这里没有任何 transfer 操作
    // 钱留在合约地址里，这就是"托管"
}
```

**关键点**：函数执行完，钱还在合约账户上。卖家调用 `getUserInfo()` 会发现余额没变。

#### confirmReceived() —— 放款

```solidity
function confirmReceived(uint256 _itemId) public itemExists(_itemId) {
    Item storage item = items[_itemId];

    require(item.status == ItemStatus.InEscrow, "Item is not in escrow");
    require(item.buyer == msg.sender, "Only the buyer can confirm receipt");

    uint256 fee = (item.price * platformFeeRate) / 10000;
    uint256 sellerAmount = item.price - fee;

    // 【重要】先改状态，再转账
    item.status = ItemStatus.Sold;
    users[item.seller].soldCount++;
    users[item.buyer].boughtCount++;

    // 后转账
    item.seller.transfer(sellerAmount);
    if (fee > 0 && owner != address(0)) {
        payable(owner).transfer(fee);
    }
}
```

**为什么"先改状态再转账"**：这是防御**重入攻击**的标准写法。如果先转账，恶意合约可以在收到钱的回调里再次调用 `confirmReceived()`，把钱重复提走。先改状态确保第二次调用时 `require` 会失败。

这是智能合约安全的经典考点，答辩时值得强调。

### 3.4 权限控制矩阵

| 操作 | 谁能做 | 合约里的检查 |
|---|---|---|
| 注册 | 任何人 | 未注册过 |
| 上架商品 | 已注册用户 | `onlyRegistered` |
| 购买 | 已注册用户 | 不能买自己的、金额必须匹配 |
| 确认收货 | **只有买家** | `require(item.buyer == msg.sender)` |
| 下架 | **只有卖家** | `require(item.seller == msg.sender)` |
| 评价 | 交易双方 | 只能是双方之一、不能评自己、不能重复评 |
| 改手续费 | 平台方 | `require(msg.sender == owner)` |

## 四、安全设计

### 4.1 应用层安全（登录鉴权）

合约层保证了"链上操作本身不可伪造"，但如果**谁都能声称自己是别人**，合约的权限检查就形同虚设。这是本项目补上的一层。

#### 改造前的漏洞

最初版本的登录只有一行：

```javascript
state.username = input.value;   // 前端说了算
```

后端所有接口都从请求体读身份：

```python
username = data.get("username")     # ❌ 前端说啥就是啥
```

**后果**：任何人打开控制台，构造
```json
{"username": "alice", "item_id": 3}
```
就能以 Alice 的身份下单、下架 Alice 的商品、用 Alice 的名义给对方打分。链上的 `require(item.seller == msg.sender)` 校验依然是"通过"的 —— 因为后端**真的用 Alice 的私钥签了名**。

> 这是区块链应用最容易踩的坑：**链上安全 ≠ 应用安全**。合约再严密，被一个恶意前端绕过去，也就是个摆设。

#### 改造后的四层防护

**第 1 层 · 密码 scrypt 加盐哈希**

```python
# backend/auth.py
SCRYPT_N, SCRYPT_R, SCRYPT_P, SCRYPT_DKLEN = 2**13, 8, 1, 32

def hash_password(password: str) -> str:
    salt = secrets.token_bytes(16)                       # 每账号独立随机盐
    dk = hashlib.scrypt(password.encode(), salt=salt,
                        n=SCRYPT_N, r=SCRYPT_R, p=SCRYPT_P, dklen=SCRYPT_DKLEN)
    return f"scrypt${b64(salt)}${b64(dk)}"

def verify_password(password: str, stored: str) -> bool:
    _, salt_b64, hash_b64 = stored.split("$")
    dk = hashlib.scrypt(password.encode(), salt=b64d(salt_b64), ...)
    return hmac.compare_digest(dk, b64d(hash_b64))       # 恒定时间比较
```

三个设计点：

| 设计 | 防御什么 |
|---|---|
| **随机盐**（16 字节/账号） | 彩虹表反查；相同密码在库里哈希也不同 |
| **scrypt 计算密集**（约 90ms/次） | 离线暴力枚举：GPU 每秒能试的密码数被压到极低 |
| **`hmac.compare_digest`** | 计时攻击：普通 `==` 会在首个不同字节处提前返回，测响应时间可逐字节猜出哈希 |

> **参数取舍**：scrypt 的 `N` 每翻一倍，耗时约翻倍。实测 N=2¹⁴ → 190ms，登录时肉眼可见卡顿；N=2¹³ → 90ms；N=2¹² → 47ms。选 2¹³ 作为演示环境的平衡点，代码里留了注释。真实生产系统应取 2¹⁵ 以上并做压测调优。

**第 2 层 · HMAC 签名令牌（无状态）**

不引入数据库，用签名保证 token 不可伪造：

```
token  = base64url(载荷) . base64url(HMAC-SHA256(载荷, 服务端密钥))
载荷    = {"u": 用户名, "iat": 签发时间, "exp": 过期时间, "jti": 随机ID}
```

验证顺序很关键 —— **先验签名，再看内容**：

```python
def verify_token(token):
    payload_b64, sig_b64 = token.split(".")
    expect = hmac.new(SECRET, payload_b64.encode(), sha256).digest()
    if not hmac.compare_digest(b64d(sig_b64), expect):
        return None, 0                    # 签名不对，直接拒绝
    payload = json.loads(b64d(payload_b64))
    if time.time() > payload["exp"]:
        return None, 0                    # 过期了
    return payload["u"], payload["exp"] - time.time()
```

- **有效期 2 小时**，剩余不足 15 分钟时自动在响应头 `X-Renewed-Token` 里下发新 token，前端静默替换 → 用户无感知续期
- **登出**把当前 token 记入服务端黑名单集合，立即失效
- **密钥来源**：优先环境变量 `MARKET_SECRET_KEY`，否则生成后持久化到 `backend/.secret_key`（下次重启不失效）

**第 3 层 · 身份只认 token**

```python
def require_auth(view):
    @wraps(view)
    def wrapper(*args, **kwargs):
        token = extract_token()                      # 支持 3 种携带方式
        username, remain = auth.verify_token(token)
        if not username or token in state.revoked_tokens:
            return jsonify({...}), 401
        request.auth_user = username                 # 注入可信身份
        ...
```

`extract_token()` 按优先级找 token：`Authorization: Bearer xxx` 头 → 请求体字段 → URL 参数（兼容 multipart 上传和 GET 请求）。

挂载的 8 个接口及各自约束：

| 接口 | 用途 | 额外校验 |
|---|---|---|
| `POST /api/logout` | 登出 | — |
| `GET /api/me` | 查询我是谁（刷新恢复登录态） | — |
| `POST /api/items` | 上架 | 卖家 = token 身份 |
| `POST /api/buy` | 下单 | 买家 = token 身份 |
| `POST /api/confirm` | 确认收货 | 买家 = token 身份 |
| `POST /api/remove` | 下架 | 卖家 = token 身份 |
| `POST /api/rate` | 评价 | 评价人 = token 身份，且不能评自己 |
| `GET /api/my_items` | 我的交易 | **服务端过滤**，只返回与自己相关的 |

> 最后一个接口值得单独说：它不在前端过滤，而是后端只挑出 `seller == me or buyer == me` 的记录。前端过滤只是"藏起来"，改个请求就能拿到全量数据。

**第 4 层 · 防暴力破解**

```python
MAX_FAILURES    = 5           # 5 次
FAILURE_WINDOW  = 5 * 60      # 5 分钟窗口内
LOCKOUT_DURATION = 5 * 60     # 锁定 5 分钟
```

滑动窗口计数：窗口内失败满 5 次即锁定，锁定期间**密码正确也返回 429**（否则攻击者仍可继续试探）。

另外，**用户名不存在和密码错误返回完全相同的提示**，避免通过响应差异枚举出哪些用户名已被注册。

#### 实测拦截效果

| 攻击 | 结果 |
|---|---|
| Bob 拿自己的 token，请求体写 `username: "alice"` 下单 | 链上买家是 **Bob** —— 冒名失败 |
| 不带 token 上架 | `401 登录已失效，请重新登录` |
| 篡改 token 签名末 4 位 | `401` |
| 仅提交去掉签名的裸载荷 | `401` |
| 连错 5 次后再输正确密码 | `429` 锁定 |
| 登出后用旧 token 请求 | `401` |
| 检查公开接口响应 | 无密码、无哈希、无 token 泄漏 |

#### 一个刻意的取舍

链重置（`/api/reset`）**不清空账号密码**：

```python
def reset(self):
    self.user_sessions.clear()
    self.nicknames.clear()
    self.revoked_tokens.clear()
    # self.credentials 不动 —— 否则每次重置都要重新注册所有账号
```

代价是重置后用户名仍被占用。演示时的正确做法是**用原账号登录**（会自动分配新的链上账户）。这是"演示便利性 vs 数据彻底性"的取舍，代码里写了注释说明。

### 4.2 合约层已防御的攻击类型

| 攻击 | 防御手段 | 代码位置 |
|---|---|---|
| **重入攻击** | 先改状态后转账 | `confirmReceived()` |
| **越权操作** | 修饰器 + require 检查 | 各函数 |
| **重复购买** | 状态机检查 | `buyItem()` |
| **重复评价** | 映射记录已评价 | `hasRated` |
| **金额欺骗** | 严格相等校验 | `require(msg.value == item.price)` |
| **卖家自购刷单** | 地址比对 | `require(item.seller != msg.sender)` |
| **评分越界** | 范围校验 | `require(_score >= 1 && _score <= 5)` |
| **整数溢出** | Solidity 0.8+ 内置检查 | 编译器层面 |

### 4.3 已知局限

诚实地说，本项目作为教学演示，有以下局限：

1. **token 无法主动批量吊销**：无状态签名的固有特性 —— 服务端不存 session，只能靠黑名单逐个作废已登出的 token。本项目把黑名单落盘了（含过期时间，加载时自动清理），所以重启后登出依然有效；但名单本身存在 JSON 文件里，量大以后性能会退化，生产系统应该用 Redis。
2. **没有找回密码流程**：真实系统需要邮箱/短信验证码。
3. **token 存 localStorage**：简化了实现，但 localStorage 可被 XSS 读取。更安全的做法是 `HttpOnly` Cookie + CSRF Token。
4. **没有 HTTPS**：本地演示用 HTTP。生产环境必须 HTTPS，否则 token 在网络中明文传输。
5. **图片是本地内容寻址，不是真 IPFS**：图片按 SHA-256 内容寻址存储，原理与 IPFS 一致，但没有接入 IPFS 分布式网络（IPFS 节点会触发系统应用控制策略拦截）。图片本体存在 `uploads/` 目录，只有哈希上链。生产系统中图片应真正存到 IPFS 或对象存储，链上只存 CID。
6. **图片未做病毒/内容扫描**：只校验了扩展名和大小，未做实际内容类型检测。
7. **没有争议仲裁机制**：如果买家一直不确认收货，钱会永久锁在合约里。生产系统需要超时自动退款或第三方仲裁。
8. **测试环境不是真实链**：本地链没有网络共识、没有矿工费竞争，安全性论证不适用于生产环境。
9. **看板是实时全量扫描**：每次打开看板都会遍历全部商品和事件，商品量大时会有性能问题。生产系统应建立事件索引（如 The Graph）或缓存层。
10. **账户仍是固定池子（200 个）**：虽然从 10 提到了 200（可注册 199 位用户），但本质还是"从池子里发账户"，不是"一人一个派生账户"。生产系统应该用助记词/私钥派生，池子就不存在上限了。
11. **没有 HTTPS**：局域网演示用 HTTP，密码和 token 都是明文传输。**不要放到公网上**。
12. **「重置整条链」接口没有鉴权**：页面上任何人都能点。生产环境必须加管理员角色校验。
13. **SQLite 单进程写入**：链数据落在 SQLite 上，多进程同时写会冲突。本项目是单进程 + 多线程，没问题；要横向扩展得换成真正的链节点（Geth / Reth）。

## 五、实现要点

### 5.0 登录态的健壮性设计

演示项目最容易被忽略、但实际最影响体验的一点：**"我的登录怎么老是失效"**。

排查下来这不是单点 bug，而是三个原因叠加。修复思路是把「状态不一致」变成「可自愈」：

**问题一：链重置后地址映射丢失**

```
用户登录       → user_sessions = {"alice": 0x2B5A...}
点「重置整条链」→ 链重建，user_sessions 被清空
用户的操作请求  → token 签名验证通过 ✓、账号也存在 ✓
                 但 addr_of("alice") == None → 找不到链上地址 → 报错
```

关键在于：token 是**无状态**的，它只证明"你是 alice"，**不携带链上地址**。地址是在服务端 `user_sessions` 里维护的映射。

**修复**：新增 `state.ensure_account(username)` —— 发现地址没了就**重新分配一个**（`get_account` 本就有"已存在则复用、不存在则新建"的语义），而不是报错把用户踢下线。`require_auth` 装饰器在所有受保护接口上自动做这件事。

**问题二：错误码语义混乱**

修复前，同一种"查不到地址"在不同接口上返回：

| 接口 | 修复前 | 修复后 |
|---|---|---|
| 4 个写接口 | `400 账号异常，请重新登录` | `503 ACCOUNT_POOL_FULL` |
| `/api/me` | `404 账号不存在` | `503 ACCOUNT_POOL_FULL` |
| `/api/register` | `400 ACCOUNT_POOL_FULL` | `503 ACCOUNT_POOL_FULL` |

前端根本没法统一处理。现在收敛为两个明确语义：

- `401 AUTH_REQUIRED` —— 令牌**真的**失效了（签名错/过期/已登出），请重新登录
- `503 ACCOUNT_POOL_FULL` —— 令牌**没问题**，只是演示账户发完了，**不能**把用户踢下线

**问题三：掉线后没有登录入口**

修复前，被踢下线时 `api()` 只弹一个一闪而过的 toast，而登录卡片已经被换成了只读的用户条 —— 用户想重新登录只能手动刷新页面。

**修复**：新增 `AUTH_FORM_TEMPLATE`（登录表单的 HTML 模板）+ `renderAuthForm()`（原地重建表单）+ `bindAuthForm()`（重建后重绑事件，因为 `innerHTML` 一换，旧监听器全部失效）。掉线时把原因写进表单上的提示条，用户看到的是"登录已失效，请重新登录" + 一个能立刻用的登录框。

> **顺带修掉的坑**：「重置整条链」按钮以前用 `location.reload()` 整页刷新，等于静默把用户丢回登录页。现在改为原地复原表单 + 明确提示原因。

**问题四：带图片上架漏带令牌（2026-10-11 补修）**

上面三个问题修完后，用户反馈**「上架商品仍会弹出登录已失效」**。这次的触发条件很具体：**只有附了图片才会**。

原因在上架的提交分支上 —— 前端有两条路：

```javascript
// 不带图片：走 post() → api()，会自动带 Authorization
r = await post('/api/items', { name, description, category, price_eth });

// 带图片：用 multipart 提交。这里当初直接写了裸 fetch，漏了令牌！
const res = await fetch(API + '/api/items', { method: 'POST', body: fd });
```

裸 `fetch` **绕过了 `api()` 封装**，因此既没带 `Authorization: Bearer <token>`，也不享受统一错误处理。后端 `@require_auth` 收到无令牌请求 → `401 AUTH_REQUIRED` → 前端弹「登录已失效」。

实测对照（修复前）：

| 提交方式 | 结果 |
|---|---|
| 不带图片（走 `post()`） | ✅ 200 上架成功 |
| **带图片（裸 fetch）** | ❌ **401 登录已失效** |

**修复**：把那条分支也改成走 `api()`，并补了注释说明「不要手动设 Content-Type，浏览器会自己带 multipart 边界」。同时在失败分支里避免重复弹提示（`api()` 已经处理过 `AUTH_REQUIRED` / `ACCOUNT_POOL_FULL`）。

**防回归**：新增 `scripts/test_publish_auth.js`，除了验证「带图/不带图都带令牌」，还**静态扫描全站**是否存在绕过 `api()` 的裸 `fetch`（允许的例外只有 `api()` 自身和无需鉴权的 `/api/upload`）—— 这类"某条分支忘了鉴权"的 bug 靠人工 review 很容易漏，用测试锁住。

### 5.05 链数据持久化（重启不丢）

早期版本用的是纯内存链：**进程一关，商品、订单、余额全没了**。
这对"反复演示"是优点，但对"真的给同学用"是致命的 —— 没人能接受
今天上架的东西明天就不见了。

#### 切入点：py-evm 留的后端注入口

难点在于这条链是 py-evm 的 `MiningChain`，它内部的状态是一个层层包装的
对象树，**没法直接序列化**（实测 `pickle.dumps(chain)` 会报
`Can't get local object 'setup_tester_chain.<locals>.MainnetTesterPosChain'`）。

但 py-evm 建链时有个官方注入点：

```python
# eth/db/__init__.py
def get_db_backend_class(import_path: str = None):
    if import_path is None:
        import_path = os.environ.get("CHAIN_DB_BACKEND_CLASS", DEFAULT_DB_BACKEND)
    return import_string(import_path)
```

也就是说，**只要设置环境变量 `CHAIN_DB_BACKEND_CLASS` 指向自己的类，
整条链的底层存储就能换掉**。

#### 实现

`backend/chaindb.py` 做了两件事：

```python
class SqliteKV(MutableMapping):
    """SQLite 支撑的 bytes→bytes 字典，接口与 dict 完全一致"""
    # py-evm 的 MemoryDB 内部只认一个 Dict[bytes, bytes]（属性名 kv_store），
    # 塞一个 MutableMapping 进去即可，py-evm 完全不知道底层换了

class SqliteAtomicDB(AtomicDB):
    def __init__(self, wrapped_db=None, path=None):
        if wrapped_db is None:
            wrapped_db = MemoryDB(kv_store=SqliteKV(path or DB_PATH))
        super().__init__(wrapped_db)
```

然后 `chaindb.install()` 在建链前设一次环境变量即可。

这样落盘的是**整条链本体**：区块、交易回执、事件日志、合约存储。
不需要写"快照 → 重启 → 回放重建"那套逻辑，也就不会丢事件日志
（时间线功能正是靠事件日志还原的）。

#### 一个必须验证的假设

重开已有数据库时要传入同样的 `genesis_state`，这会重新写一次创世块。
**会不会把链头拉回 0？** 如果会，持久化就白做了。

实测（`scripts/_probe_reattach.py`）结论是不会 —— 创世块是确定性生成的，
重复写入是幂等的：

```
链头保住        : ✓（区块高度 1 保持为 1）
余额保住        : ✓（107 ETH 保持 107）
账户数正确      : ✓
```

#### 原子性与并发

- **原子性**：`AtomicDBWriteBatch` 会把写入缓冲在内存 diff 里，退出上下文
  时才一次性 apply。所以只要把 apply 包进 SQLite 事务，就能拿到真正的
  原子性 —— 中途抛异常整批回滚，不会出现"写了一半"的链状态。
  支持嵌套（外层 `BEGIN`，内层 `SAVEPOINT`），因为 py-evm 出块时会开批次、
  批次里还会再开子批次。
- **并发**：链本身不是线程安全的（`chain.header`、`mine_block` 都在改共享
  状态），waitress 是多线程的，两个人同时下单可能把链改乱。
  所以所有上链操作统一走 `chain_tx()`，内部用一把全局 `RLock` 串行化。
  局域网十几个人用，这点串行开销远小于状态错乱的代价。

#### 为什么清空数据用 `DELETE` 而不是删文件

waitress 的每个工作线程都持有自己的 sqlite 连接，**Windows 上文件被占用
时删不掉**（`PermissionError`）。所以 `clear_db()` 是清空表内容，
效果相同但对各线程已打开的连接是安全的。

### 5.06 「记住我」：长令牌与登出黑名单

用户提「让项目记住密码（重启后无需重新注册）」。核实后发现要分两件事看：

**① 账号密码** —— 早就落盘了（5.05）。重启服务后直接登录即可，
**并不需要重新注册**。误解来自界面上那句旧文案
「本平台密码只存在后端内存，重启后需重新注册」，已改掉。

**② 登录态** —— 这个才是真问题。令牌默认只有 **2 小时**，
所以第二天打开确实要重新登录。这才需要「记住我」。

#### 设计

| | 不勾「记住我」 | 勾上 |
|---|---|---|
| 令牌有效期 | 2 小时 | 30 天 |
| 记住用户名 | 否 | 是 |
| 存密码吗 | **否（两种都不存）** | **否** |

**密码绝不落 localStorage。** 只存用户名 + 令牌。理由：localStorage 可被
XSS 直接读取，密码明文一旦存在那里，等于把所有账号交出去。
记住用户名只是省几次敲键盘，风险可接受；记住密码则完全不可接受。

#### 一个容易漏掉的连带问题

登出是靠「把令牌加进黑名单」实现的（无状态令牌没法真正删除）。
以前黑名单只在内存里 —— 2 小时令牌问题不大，但**30 天令牌不落盘的话，
登出后一重启就又活过来了**，等于登出功能失效。

所以黑名单改成了 `{token: 过期时间}` 并落盘，加载时自动丢掉已自然过期的条目
（到点了本来就无效，留着只会让文件无限增长）：

```python
self.revoked_tokens = {
    t: exp for t, exp in (meta.get("revoked_tokens") or {}).items()
    if not exp or exp > now
}
```

#### 被动掉线不该清空用户名

`clearAuth()` 加了一个参数区分两种场景：

- **主动登出**（`clearAuth(true)`）：连记住的用户名一起清掉 —— 换人用同一台
  电脑时更安全
- **令牌过期导致的被动掉线**（`clearAuth()`）：保留用户名，否则用户还得
  重新敲一遍用户名，白「记住」了

### 5.1 为什么用 eth-tester 而不是 Ganache

原计划用 Ganache（业界标准工具），但遇到问题：

- Ganache 是 Node.js 包，安装后包含二进制文件
- 用户系统启用了 Windows 智能应用控制（WDAC），会拦截未建立信誉的新二进制

于是改用 `eth-tester`——纯 Python 实现的以太坊虚拟机，功能等价，零外部依赖。

**这本身就是一次工程决策**：当标准方案在特定环境下不可行时，找到满足需求的最小替代方案。

### 5.2 中文编码问题

Solidity 编译器（0.8.19）不接受源码中出现非 ASCII 字符的字符串字面量。最初合约里写了中文错误提示，编译直接报错。

**解决方案**：合约层用英文，后端做翻译映射：

```python
ERROR_MAP = {
    "Please register first": "请先注册账号",
    "Item is not on sale": "该商品不在售",
    # ...
}

def translate(msg):
    for en, zh in ERROR_MAP.items():
        if en in msg:
            return zh
    return msg
```

这样合约代码干净、符合规范，用户体验仍是中文。**分层处理不同关注点**。

### 5.3 用户系统设计

#### 地址映射层

区块链地址是 42 位十六进制字符串，用户不可能记住。解决方案：

```
用户注册 username + password
        ↓
后端按注册顺序分配 accounts[1], accounts[2], ...
        ↓
建立映射 user_sessions["zhangsan"] = "0x2B5A..."
        ↓
后续所有操作自动带上对应账户签名
```

其中 `accounts` 是 eth-tester 提供的测试账户池，私钥由本地节点托管 —— 这是**模拟钱包**，与真实 DApp 的 MetaMask 签名流程原理相同（都是"证明你是某个地址的主人"），只是省去了密钥管理。

#### 初始余额的设定

eth-tester 默认给每个账户 100 万测试 ETH。这个数字在演示里毫无意义 —— 界面上显示「余额 999999.998296162 ETH」，既看不出资金变化，也让"托管了 0.3 ETH"这种关键论据被淹没。

所以后端在启动时把每个账户的余额统一改成 **100 ETH**（`INITIAL_BALANCE_ETH`）。100 覆盖了商品价格区间（0.05 ~ 3.2 ETH），够买卖几十次，读数也直观。

有两个办法，本项目**早期用的是后者，现在改成了前者**：

**① 写进创世状态（现在的做法，推荐）**

在创建链的时候就把余额定好：

```python
keys = get_default_account_keys(quantity=NUM_CHAIN_ACCOUNTS)
genesis_state = generate_genesis_state_for_keys(
    keys, overrides={"balance": INITIAL_BALANCE_ETH * 10**18})
backend = PyEVMBackend(genesis_state=genesis_state)
```

干净、无副作用，不碰任何内部实现。

**② 建完链再改底层状态（早期做法，已弃用）**

不能用转账来调余额 —— 每笔转账都要付 gas，转完余额会差出零点零零几 ETH，凑不出整数；而且来回转账会把中间账户的余额堆到离谱的量级（试过，平台账户涨到 999 万）。

所以早期是直接改写底层状态，要穿透 py-evm 的三层封装：

```python
# 1. 在账户 trie 里写入新的 Account（余额改成目标值）
for addr in self.accounts:
    canonical = to_canonical_address(addr)
    account = account_db._get_account(canonical)
    account_db._trie[canonical] = rlp.encode(
        account.copy(balance=target_wei), sedes=Account)

new_root = account_db._trie.root_hash

# 2. 落盘 —— trie 的改动堆在 BatchDB（journal）里，不 flush 的话读不到
batch_db = account_db._trie.db
memory_db = batch_db.wrapped_db.wrapped_db.wrapped_db
batch_db.diff().apply_to(memory_db)

# 3. 把新 root hash 写进区块头再出块，状态才算固定
chain.header = chain.header.copy(state_root=new_root)
chain.mine_block()
```

关键在第 3 步：`chain.get_vm()` **每次都重新构造一个 State 对象**，状态根取自当前区块头。只改 trie 不改 header，读余额时仍然走旧的 root，看起来就像"没生效"。这一点排查了很久。

**弃用原因**：这套写法依赖 `_trie`、`BatchDB`、`wrapped_db.wrapped_db.wrapped_db` 一串内部实现，
换个 py-evm 版本就可能失效；而且会额外产生 1 个区块。改成写创世状态后，
两个问题一起消失。

> 平台方账户最终显示 99.998 ETH 左右，差额是部署合约消耗的 gas —— 这是真实发生的，不是 bug。

#### 认证层的演进

需要说明的是，**"用户名 → 地址"的映射本身不构成认证**。它只回答了"这个用户名对应哪个地址"，没回答"你凭什么说你是这个用户名"。

两者是正交的，必须分开：

| 层 | 职责 | 数据 |
|---|---|---|
| **认证层** | 证明"你是这个用户名" | `credentials[username] = "scrypt$盐$哈希"` |
| **映射层** | 用户名 → 链上地址 | `user_sessions[username] = "0x2B5A..."` |

请求进来时的完整链路：

```
请求头 Authorization: Bearer <token>
        ↓
① auth.verify_token()  →  验签名 + 验过期  →  得到 username
        ↓
② state.addr_of(username)  →  映射层查地址  →  得到 0x2B5A...
        ↓
③ 用该地址签名上链（from=0x2B5A...）
        ↓
④ 合约的 require(seller == msg.sender) 才是真正生效的
```

关键在第 ①步：**username 是密码学验证出来的，不是前端给的**。这才让第 ④ 步的合约校验有意义。

> **反过来说**：如果第 ① 步被绕过（改造前就是从请求体读 username），第 ④ 步无论多严密都会被跳过 —— 因为后端是"真的"用受害者的私钥签了名。这就是为什么链上安全必须配上应用层认证。

### 5.4 图片的内容寻址

图片存储采用了与 IPFS 相同的核心思路：**地址由内容决定**。

```python
digest = hashlib.sha256(data).hexdigest()   # 算出内容指纹
stored_name = digest + ext                  # 用指纹当文件名
if not target.exists():
    target.write_bytes(data)                # 已存在就不重复写（天然去重）
```

这个设计带来的性质：

| 性质 | 原理 |
|---|---|
| 去重 | 内容相同 ⇒ 哈希相同 ⇒ 同一文件名，不会存两份 |
| 防篡改 | 内容差一个字节 ⇒ 哈希完全不同，与链上记录对不上 |
| 可校验 | 重新哈希磁盘文件，与链上哈希比对即可验证完整性 |

**哈希如何上链而不改合约**：合约的 `description` 是 `string`，我们把分类和哈希编码进去：

```
[分类]数码电子|473ad193...949e|这台耳机九成新
 └─分类──┘ └──图片哈希──┘ └──真实描述──┘
```

写入前 `encode_description()` 拼接，读取时 `decode_description()` 解析（兼容 3 种历史格式）。**加字段不用重新部署合约**，这是区块链应用开发中处理"合约不可更改"的实用手法。

### 5.5 时间线为什么可信

交易时间线不是后端维护的一张 `timeline` 表，而是**从链上事件日志重建**的。

合约在每个关键动作处 `emit` 事件：

```solidity
event ItemListed(uint256 indexed itemId, address indexed seller, string name, uint256 price);
event ItemPurchased(uint256 indexed itemId, address indexed buyer, uint256 amount);
event ItemDelivered(uint256 indexed itemId, address indexed buyer);
event Rated(address indexed from, address indexed to, uint256 indexed itemId, uint8 score);
```

`indexed` 关键字让 `itemId` 进入日志的 topic，于是可以按商品 ID 高效过滤：

```python
logs = market.events.ItemPurchased.get_logs(
    from_block=0, argument_filters={"itemId": item_id})
```

然后按区块号排序，就还原出完整流转。**关键区别**：后端即使被入侵，也无法伪造这条时间线 —— 因为数据源在链上，事件一旦写入就无法更改。这正是"用区块链做存证"的价值所在。

### 5.6 看板为什么不做缓存

数据看板每次都**重新遍历链上数据现算**：

```python
for i in range(1, count + 1):
    raw = market.functions.getItem(i).call()
    # 累加成交额、分类统计、价格分桶...
```

好处是永远不会出现"看板数据和链上不一致"的问题 —— 因为根本没有第二份数据。代价是 O(n) 遍历，商品量大时会慢。生产环境的正确做法是用 The Graph 之类的索引服务订阅事件、建立物化视图。

**这是一个有意识的权衡**：演示场景下数据量小（几十条），实时计算的正确性比性能更重要。

## 七、可扩展方向

如果要把这个项目继续做下去：

1. **接入 IPFS 存图片** —— 商品图片上传 IPFS，链上只存哈希，解决链上存储成本问题
2. **争议仲裁机制** —— 引入第三方仲裁者，买家不确认收货时可以申请仲裁
3. **超时自动退款** —— 加入时间锁，卖家长期不发货则合约自动退款
4. **迁移到公链测试网** —— 部署到 Sepolia 测试网，让其他人也能访问
5. **接入真实钱包签名** —— 用 MetaMask 的 `personal_sign` 让用户用自己的私钥签名，替代"服务端托管私钥 + 令牌"的折中方案。这样连平台方都无法代替用户发起交易，是真正意义上的去中心化
6. **令牌改用 HttpOnly Cookie** —— 当前存 `localStorage` 有 XSS 读取风险，改用 `HttpOnly` Cookie + CSRF Token 更稳妥；同时上 HTTPS
7. **令牌吊销列表外置** —— 当前黑名单在内存里，重启即失效。生产环境应放 Redis
8. **商品分类与搜索索引** —— 后端加索引，支持按类别、价格区间筛选
